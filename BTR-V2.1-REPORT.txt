CONFIRMED ROOT CAUSES

A. SITTER FOOD/MEDICATION FILTER
The supplied build still contained:
  feedingItems.slice(0,1)
  medications.filter(...).slice(0,1)
Therefore only one food and one medication could ever appear in Sitter Mode.

REPAIR
Explicit active flags are now supported and synchronized.
Sitter Mode filters all active foods and all active medications.

B. SITTER MODE AFTER IPHONE APP SUSPEND
The supplied build relied on pageshow/pagehide/visibility timing and a foreground dismissal flag.
A standalone iOS PWA can be frozen and restored without delivering that event sequence reliably, leaving the old in-memory dismissal flag intact.

REPAIR
Added independent reassertion plus a timer-gap heartbeat. When JavaScript timers resume after a freeze gap, active sitter mode is treated as a fresh entrance.

C. CONNECTION SETUP
The supplied build displayed the manual family code field whenever no local connection code existed.
That made the recovery path look like the normal login.

REPAIR
- normal setup displays name/initials only
- manual connection code is hidden behind a recovery link
- setup URL provisioning is mirrored to a secure same-origin cookie as well as localStorage
- stored cookie values can restore the local connection/user keys

LIMIT
A completely unprovisioned device still needs either the one-time setup link or the family code once. Removing both would require exposing the credential in public source or changing the backend pairing design.

D. CURRENT STATE WAS INFERRED FROM DISPLAY ORDER
The old compact Care presentation treated later array items as “previous,” but that does not model simultaneous current foods or medications correctly.

REPAIR
Current is explicit data.
Migration gives older data a safe starting state:
- newest feeding item per category Current
- ongoing/non-expired medications Current
Users can explicitly alter Current afterward.
